# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

be-sql parses the BE-SQL dialect for BeanExplorer 5 (https://github.com/DevelopmentOnTheEdge/be5) (CRUD queries, PostgreSQL-like syntax plus BE-specific XML-ish tags such as `<if>`, `<unless>`, `<param>`, `<sql>`) into an AST, then formats that AST into concrete SQL for a target DBMS (DB2, MySQL, Oracle, PostgreSQL, SQL Server, H2).

## Build & test commands

- `mvn -B clean test` — full build: JavaCC generation, checkstyle, tests
- `mvn test -Dtest=ParserXmlTest` — run one test class
- `mvn compile` — regenerate JavaCC sources without running tests
- `mvn checkstyle:check` — style check only (config: `checkstyle.xml`; runs in the `validate` phase, fails the build on violations)
- `mvn -DskipTests deploy -Pcentral-publish` — deploy to Maven Central (requires GPG + `central` server id)

Java 8 source/target. The `xmltest` test dependency (`com.developmentontheedge:xmltest`) is NOT on Maven Central — CI clones and installs it from https://github.com/DevelopmentOnTheEdge/xmltest first. Locally: `mvn install` it (skipping tests/javadoc) into `~/.m2` before building, or tests will not resolve.

## Architecture

The pipeline is: **parse → transform (apply) → format**.

1. **Parse.** `src/main/jjtree/com/developmentontheedge/sql/model/SqlParser.jjt` is the JavaCC grammar (the only file you edit for new syntax). It is generated at build time by `javacc-maven-plugin` into `target/generated-sources/jjtree` and `target/generated-sources/javacc`. **Do not hand-edit anything under `target/generated-sources` or any file marked `Generated By:JJTree`** (e.g. `SimpleNode.java`, `AstStart.java`, `AstBeNode.java`) — regenerate instead.

   - `SqlParser` (generated) extends `AbstractParser` (`src/main/java/.../sql/model/AbstractParser.java`), which owns error/warning collection, a push/pop `Mode` stack (used to disambiguate syntax inside BE tags vs. normal SQL), and a "squash" pass that collapses single-child `AstBeNode` wrappers.
   - Entry point: `SqlQuery.parse(String)` (`src/main/java/.../sql/model/SqlQuery.java`) → `AstStart`. It throws `IllegalArgumentException` if the parse produced any messages. `parser.parse(String)` returning `STATUS_OK/WARNING/ERROR` is the lower-level API.
   - Node classes are the `Ast*.java` files under `src/main/java/.../sql/model/`. All extend `SimpleNode`. The AST is a **format-preserving tree**: `SimpleNode` tracks first/last tokens and "special" (whitespace/comment) tokens, so `node.format()` re-emits SQL close to the original spacing.
   - `AstBeNode` is the base for BE tag nodes (`<if>`, `<unless>`, `<param>`, `<sql>`, `<sqlsubquery>`, …) and carries tag parameters.
   - Function/operator knowledge lives in `ParserContext` / `DefaultParserContext` (`sql/model/`): a registry of `PredefinedFunction`, `BeMacroFunction`, and `DbSpecificFunction` (the latter records which DBMS support a function). New operators/functions are declared there. `Mode.DBMS_TRANSFORM` lets `<dbms>` tags declare per-DBMS functions on the fly.

2. **Transform.** Stateless "applier" classes in `src/main/java/.../sql/format/` mutate a *clone* of the AST:
   - `MacroExpander` — expands BE macros (run right after parsing; the XML test harness does this automatically).
   - `ContextApplier` (`new ContextApplier(QueryContext).applyContext(astStart)`) — evaluates BE tags against a `QueryContext`: `<if>/<unless>` branch selection, `<param>` substitution, `<sessionvar>`, placeholders, `<sql>`/`<sqlsubquery>` inclusion (resolved via `QueryContext.resolveQuery`), and adds filters from subquery `filterKeys`/`filterValProperties`. `BasicQueryContext` (with its `Builder`) is the standard `QueryContext` implementation: parameters, session variables, user name, roles, and subqueries.
   - `CountApplier`, `LimitsApplier`, `FilterApplier`, `ColumnsApplier`, `DistinctApplier`, `Simplifier` — smaller, single-purpose AST rewrites.

3. **Format.** `Formatter.format(ast, new Context(dbms), parserContext)` (`sql/format/dbms/`) clones the AST, runs the DBMS's `DbmsTransformer` (e.g. `MySqlTransformer`, `OracleTransformer`; common logic in `GenericDbmsTransformer`), then calls `clone.format()`. `GenericDbmsTransformer.transformFunction` is where cross-DBMS function rewriting happens (concat/coalesce/substr/date functions, etc.). A `DbSpecificFunction` that is not applicable to the target DBMS is a hard error.

## Tests

Two independent styles — pick by what you changed:

- **XML-driven integration tests** (the main suite): `ParserXmlTest` drives the whole pipeline against XML case files in `src/test/resources/` (`core.xml` is the largest; `be.xml` covers BE tags, `functions.xml` function mapping, `payments/realty/biostore` larger scenarios). `ParserTarget` is the harness: each test element has `<query>` (parsed + macro-expanded, fails on parse errors), then optional `<applyContext>` (with `<parameter>`, `<sessionVar>`, `<userName>`, `<role>` children), `<applyCount>`, `<applyLimit count="N">`, and one or more `<format dbms="postgresql,mysql,…">` blocks whose CDATA is the exact expected output (compared line-by-line after trimming). **Adding a case = adding a `<test>` element to one of these XML files** — no Java needed.
- **Plain JUnit 4 tests** in `src/test/java/...` (e.g. `PgVectorTest`, `AstInsertTest`, `SimplifierTest`) — for narrow unit behavior.

## Conventions

- Checkstyle (`checkstyle.xml`) is enforced in the `validate` phase and blocks the build; write conforming code (4-space indent, brace on same line, etc.).
- The parser context is a **singleton** (`DefaultParserContext.getInstance()`); per-query custom functions are declared by setting a parser context with a parent on the parser, not by mutating the shared instance.
- When a change affects both parse and format, the XML cases in `src/test/resources/` usually need new entries to lock the behavior in.
- `attic/` holds retired CI config; ignore it.
